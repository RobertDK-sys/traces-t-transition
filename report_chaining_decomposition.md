# β-Chaining and Nf·b_f = Σ b_k Decomposition — Report

## 1. Context

The `algorithme_chainage_beta_vf2_1.py` and `algorithme_chainage_beta_vf2_2.py` algorithms build chains of weighted pairs `(N1_k, b1_k)` and `(N2_k, b2_k)` that successively approximate a list of targets `X0_LIST`, via:

```
xc = (N1·b1 + N2·b2) / (N1 + N2)  ≈  target x0
```

- **vf2_1**: from step 2 onward, the position `b1_k` is inherited from `b2_{k-1}`, and the weight `N1_k` is free but constrained (`N1_k ≠ N2_{k-1}` and `N1_k + N2_{k-1} ≤ N_MAX`). Search via a Stern-Brocot tree (`best_rational_bounded`).
- **vf2_2**: same coupling principle, but a NumPy-vectorized search (`best_rational_constrained`) instead of Stern-Brocot.

## 2. Key Idea: (N1_k, b1_k) and (N2_k, b2_k) Are Instances of (Nf, b_f)

Each pair `(N1_k, b1_k)` (and likewise `(N2_k, b2_k)`) is structurally identical to the equation studied previously:

```
Nf · b_f = b_1 + b_2 + ... + b_Nf
```

with `Nf = N1_k` (or `N2_k`) and `b_f = b1_k` (or `b2_k`) already **known** (fixed by the chaining), and `b_1, ..., b_Nf` to be found — each generated by the same formula `b = (asin(sign·|s2(t)|) − 2kπ)/ln2`.

A function `decompose_bf_into_bk(Nf, b_f_target, pool, ...)` was added: it searches, via simulated annealing, for `Nf` **distinct** triples `(t_k, sign_k, k_k)` minimizing `|Nf·b_f − Σb_k|`. A function `annotate_chain_with_decompositions` applies this automatically to every step of a chain, for both `b1_k` and `b2_k`.

## 3. Required Optimization: Incremental Cost

The `N1`/`N2` weights observed in real chains reach several tens of thousands (up to `N_MAX = 65536`). A naive simulated-annealing implementation recomputes `Σb_k` at every iteration — an `O(Nf)` cost per iteration, hence `O(Nf × iters)` overall, which is intractable for `Nf` of this magnitude.

The solution adopted maintains the running sum **incrementally**: at each local move (replacing one `b_k`), only the difference is applied (`new_sum = current_sum − old_b_k + new_b_k`), reducing the cost to `O(1)` per iteration. This made it possible to handle `Nf` values up to ~63,000 with residuals on the order of 10⁻⁶ to 10⁻⁵, in a few seconds per decomposition.

## 4. Pool Consistency: An Important Fix

In an earlier version, the pool used to **find the chains** (`t_max=50, k_range=5`, ~1000 candidates) was much smaller than the one used for **decomposition** (`t_max=2000, k_range=20`, 160,000 candidates). This inconsistency has been fixed: **a single pool, generated once**, now serves both purposes.

Observed effect of re-running the full sweep with this extended pool (measured on `vf2_1`):

| Interval | Anchors (small pool) | Anchors (extended pool) | Completion |
|---|---|---|---|
| `]14.542, 20.797[` | ~100 | 4000 | 100% (16/16 steps) |
| `]33.514, 13.507[` | ~200 | 8000 | 100% (10/10 steps) |
| `]21.788, 25.115[` | 44 | 1994 | 100% (14/14 steps) |

With the small pool, several chains failed before reaching all targets; with the extended pool, **every chain tested reaches 100% completion**.

## 6. Practical Limitation Found: vf2_2 Becomes Costly with an Extended Pool

The NumPy-vectorized search in `vf2_2` (`best_rational_constrained`) rebuilds an array of size `N_MAX = 65536` for every candidate tested. With the extended pool, the number of starting anchors explodes (up to 8000 on some intervals), multiplying the number of calls to this search accordingly. A full sweep of all 18 intervals with `vf2_2` and the extended pool therefore takes significant time (likely several tens of minutes), whereas `vf2_1` (Stern-Brocot search, lighter-weight) completes the same full sweep in under 30 seconds.

The correctness of `vf2_2`'s computations was verified on a bounded sample (a few anchors, 3 steps) before drawing this performance conclusion — the residuals obtained (6×10⁻⁶ and 9×10⁻⁶) confirm the algorithm remains correct; only its execution speed is affected at scale.
